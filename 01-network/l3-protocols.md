## OSPF for Data Center

> **Full OSPF deep dive**: [github.com/vikiev/OSPF](https://github.com/vikiev/OSPF)
> This section covers DC-specific OSPF topics. Go to the repo for complete OSPF mastery.

### OSPF Fundamentals Review

OSPF (Open Shortest Path First) is a link-state IGP using Dijkstra's SPF algorithm.
In the DC, OSPF is commonly used as the VXLAN underlay routing protocol.

Key OSPF concepts:
- **Router ID**: 32-bit identifier (usually a loopback IP)
- **Areas**: logical grouping to limit LSA flooding and SPF scope
- **LSA (Link State Advertisement)**: database entries describing topology
- **SPF (Shortest Path First)**: Dijkstra algorithm computes shortest path tree
- **Cost**: metric based on interface bandwidth (reference bandwidth / interface bandwidth)

### OSPF Areas

| Area Type | Characteristics |
|-----------|----------------|
| Backbone (Area 0) | All areas must connect to Area 0. Carries inter-area routes. |
| Standard | Receives all LSA types. Full routing table. |
| Stub | No Type 5 (external) LSAs. Default route injected by ABR. |
| Totally Stubby | No Type 3, 4, or 5 LSAs. Only default route from ABR. |
| NSSA | No Type 5, but allows Type 7 (NSSA external). ABR converts Type 7 to Type 5. |
| Totally NSSA | No Type 3, 4, 5. Type 7 allowed. Default route from ABR. |

> **CCIE Exam Tip:** In a DC spine-leaf underlay, you typically use a SINGLE area
> (Area 0) for all spine-leaf links. Multi-area is rarely needed because the fabric
> is small (4-20 spines/leaves). Keep it simple: all interfaces in Area 0.

### LSA Types

| Type | Name | Generated By | Scope | Content |
|------|------|-------------|-------|---------|
| 1 | Router LSA | Every router | Area | Router's interfaces, cost, neighbors |
| 2 | Network LSA | DR | Area | Multi-access network, attached routers |
| 3 | Summary LSA | ABR | Inter-area | Networks in other areas |
| 4 | ASBR Summary | ABR | Inter-area | Location of ASBR |
| 5 | AS External | ASBR | Entire AS | Redistributed external routes |
| 6 | Group Membership | - | - | MOSPF (not used) |
| 7 | NSSA External | ASBR in NSSA | NSSA area | External routes in NSSA (converted to Type 5 by ABR) |

### OSPFv3 (IPv6)

OSPFv3 runs over IPv6. Key differences from OSPFv2:
- Uses link-local addresses for neighbor adjacency
- Address-family based (can carry IPv4 and IPv6 routes)
- Authentication via IPsec (not built-in)
- Instance ID field for multiple OSPF processes per link

```nxos
feature ospfv3

interface Ethernet1/1
  ipv6 address 2001:db8::1/64
  ipv6 router ospfv3 1

router ospfv3 1
  router-id 1.1.1.1
  address-family ipv6 unicast
```

### OSPF Underlay for VXLAN

In a VXLAN fabric, OSPF provides the underlay IP connectivity between VTEPs.
The underlay must route traffic between all VTEP loopback addresses.

Design principles:
- Use /31 or /30 point-to-point links between spine and leaf
- Use loopback0 for VTEP source (stable, always up)
- All interfaces in Area 0 (single area)
- Enable `ip ospf network point-to-point` on spine-leaf links (no DR/BDR election)
- Use passive-interface on loopbacks

```nxos
feature ospf

interface loopback0
  ip address 10.255.1.1/32
  ip router ospf UNDERLAY area 0.0.0.0

interface Ethernet1/49
  ip address 10.0.0.0/31
  ip router ospf UNDERLAY area 0.0.0.0
  ip ospf network point-to-point

interface Ethernet1/50
  ip address 10.0.0.2/31
  ip router ospf UNDERLAY area 0.0.0.0
  ip ospf network point-to-point

router ospf UNDERLAY
  router-id 10.255.1.1
```

> **CCIE Exam Tip:** Use /31 subnets for point-to-point underlay links. This saves
> IP addresses (only 2 usable, no network/broadcast). Always set
> `ip ospf network point-to-point` to skip DR/BDR election on these links.

### OSPF in VRF

For L3 services (inter-VXLAN routing, L3Out), OSPF runs per-VRF:

```nxos
vrf context PROD
  vni 500001
  address-family ipv4 unicast
    route-target both auto
    route-target both auto evpn

router ospf PROD_OSPF
  vrf PROD
  router-id 10.100.1.1
  address-family ipv4 unicast

interface vlan 100
  vrf member PROD
  ip address 10.100.1.1/24
  ip router ospf PROD_OSPF area 0.0.0.0
```

### OSPF Sham-Link for VRF

In MPLS/VXLAN L3VPN designs, when two sites in the same VRF are also connected via a
backdoor link (non-MPLS), OSPF may prefer the backdoor path over the VPN path. A sham-link
creates a virtual OSPF adjacency across the VPN to make the VPN path preferred.

```nxos
router ospf PROD_OSPF
  vrf PROD
  router-id 10.100.1.1
  area 0.0.0.1 sham-link 10.100.1.1 10.100.2.1
  address-family ipv4 unicast
```

The sham-link endpoints are the loopback IPs of the two PE routers within the VRF.
OSPF treats the sham-link as a point-to-point link in the specified area, making the
VPN path an intra-area route (preferred over the inter-area backdoor path).

> **CCIE Exam Tip:** Sham-links appear when the exam gives you a VRF with a backdoor
> L2/L3 connection between two sites. If OSPF is preferring the backdoor path over
> the VXLAN/MPLS path, configure a sham-link. The sham-link endpoints must be
> reachable via the VPN (they are the VRF loopbacks or any VRF-reachable IPs).

### Graceful Restart (NSF/SSO)

NSF (Non-Stop Forwarding) with SSO (Stateful Switchover) allows OSPF to continue
forwarding during a supervisor switchover without tearing down adjacencies.

```nxos
router ospf UNDERLAY
  graceful-restart
  graceful-restart grace-period 120
```

### BFD for OSPF

BFD (Bidirectional Forwarding Detection) provides sub-second failure detection for
OSPF adjacencies. Default OSPF dead timer is 40 seconds - BFD reduces this to 50-300ms.

```nxos
feature bfd

interface Ethernet1/49
  bfd interval 50 min_rx 50 multiplier 3
  ip router ospf UNDERLAY area 0.0.0.0

router ospf UNDERLAY
  bfd
```

## BGP for Data Center

> **Full BGP deep dive**: [github.com/vikiev/BGP](https://github.com/vikiev/BGP)
> This section covers DC-specific BGP topics. Go to the repo for complete BGP mastery.

### BGP Fundamentals Review

BGP (Border Gateway Protocol) is a path-vector EGP. In the DC, BGP serves two roles:
1. **Underlay routing**: replaces OSPF/IS-IS for VTEP reachability (especially with unnumbered)
2. **EVPN control plane**: distributes MAC/IP routes for VXLAN overlay

### eBGP vs iBGP

| Feature | eBGP | iBGP |
|---------|------|------|
| AS relationship | Different AS | Same AS |
| TTL | 1 (direct) | 255 (multi-hop) |
| Next-hop | Changed to self | Preserved (unless next-hop-self) |
| AD | 20 | 200 |
| Route propagation | To all neighbors | NOT to iBGP peers (split-horizon) |

### Route Reflectors

iBGP split-horizon prevents routes learned from one iBGP peer from being advertised
to another. Route Reflectors (RR) solve this by reflecting routes to clients.

In a DC spine-leaf: spines are RRs, leaves are RR clients.

```nxos
router bgp 65000
  neighbor 10.255.2.1
    remote-as 65000
    update-source loopback0
    address-family l2vpn evpn
      route-reflector-client
      send-community extended
```

### BGP Path Selection (13 Steps)

BGP selects the best path using these criteria IN ORDER:

1. **Highest Weight** (Cisco proprietary, local to router)
2. **Highest Local Preference** (default 100, shared within AS)
3. **Locally originated** (network/aggregate/redistribute)
4. **Shortest AS_PATH**
5. **Lowest Origin type** (IGP < EGP < Incomplete)
6. **Lowest MED** (Multi-Exit Discriminator)
7. **eBGP over iBGP**
8. **Lowest IGP metric to next-hop**
9. **Oldest eBGP path** (most stable)
10. **Lowest Router ID** (or originator ID for reflected routes)
11. **Shortest cluster-list length**
12. **Lowest neighbor address**

> **CCIE Exam Tip:** You MUST know the BGP path selection order. The exam will give
> you a scenario where you need to influence path selection. Know which attribute to
> change: LOCAL_PREF for inbound, MED/AS_PATH for outbound, WEIGHT for local router.

### BGP Communities

| Type | Format | Size | Use Case |
|------|--------|------|----------|
| Standard | ASN:VALUE | 32-bit | General policy (e.g., 65000:100) |
| Extended | Type:ASN:VALUE | 64-bit | Route targets, site-of-origin |
| Large | ASN:VALUE1:VALUE2 | 96-bit | Large ASN support (4-byte ASN) |

Well-known communities:
- `NO_EXPORT` (65535:65281): do not advertise to eBGP peers
- `NO_ADVERTISE` (65535:65282): do not advertise to any peer
- `LOCAL_AS` (65535:65283): do not advertise outside local AS

```nxos
route-map SET_COMMUNITY permit 10
  set community 65000:100 additive

router bgp 65000
  neighbor 10.255.2.1
    address-family ipv4 unicast
      route-map SET_COMMUNITY out
```

### BGP EVPN (Address-Family l2vpn evpn)

BGP EVPN is the control plane for VXLAN. It distributes MAC and IP reachability
information across VTEPs.

```nxos
router bgp 65000
  neighbor 10.255.2.1
    remote-as 65000
    update-source loopback0
    address-family l2vpn evpn
      send-community extended
      route-reflector-client
```

EVPN route types (covered in detail in vxlan-evpn.md):
- RT-1: Ethernet A-D
- RT-2: MAC/IP Advertisement
- RT-3: IMET (Inclusive Multicast Ethernet Tag)
- RT-4: Ethernet Segment
- RT-5: IP Prefix

### BGP Underlay for VXLAN (Unnumbered)

BGP unnumbered uses IPv6 link-local addresses for peering, eliminating the need to
assign IPv4 addresses to every spine-leaf link. This is the PREFERRED underlay for
large VXLAN fabrics.

```nxos
feature bgp

router bgp 65000
  router-id 10.255.1.1
  neighbor fabric
    remote-as 65001
    update-source loopback0
    ebgp-multihop 2
    address-family ipv4 unicast
      send-community extended
    address-family l2vpn evpn
      send-community extended

  template peer fabric
    remote-as 65001
    update-source loopback0
    ebgp-multihop 2
    address-family ipv4 unicast
    address-family l2vpn evpn

interface Ethernet1/49
  no switchport
  ipv6 enable
  ip router ospf UNDERLAY area 0.0.0.0

router bgp 65000
  neighbor 10.255.2.1
    remote-as 65000
    update-source loopback0
    address-family ipv4 unicast
    address-family l2vpn evpn
      route-reflector-client
      send-community extended
```

BGP listen-range for dynamic peering (spine auto-discovers leaves):

```nxos
router bgp 65001
  router-id 10.255.100.1
  listen limit 100
  listen range 10.0.0.0/16 peer-group fabric
```

> **CCIE Exam Tip:** BGP unnumbered underlay is increasingly common in the exam.
> Know how to configure it: `ipv6 enable` on the interface, BGP peers using
> link-local addresses, and `ebgp-multihop 2`. The key advantage is NO IPv4
> addressing on spine-leaf links.

### BGP in VRF and BGP for L3Out

For L3 services, BGP runs per-VRF:

```nxos
router bgp 65000
  vrf PROD
    address-family ipv4 unicast
    neighbor 10.100.1.2
      remote-as 65100
      address-family ipv4 unicast
        send-community extended
```

In ACI, BGP is used for L3Out to exchange routes with external routers:
- External router peers with ACI leaf's L3Out interface
- BGP exchanges routes between ACI VRF and external network
- Route maps control which routes are imported/exported

### BFD for BGP and BGP PIC

BFD provides fast failure detection for BGP sessions:

```nxos
feature bfd

router bgp 65000
  neighbor 10.255.2.1
    bfd
    remote-as 65000
```

BGP PIC (Prefix Independent Convergence) pre-computes backup paths for fast failover:

```nxos
router bgp 65000
  address-family ipv4 unicast
    additional-paths receive
    additional-paths send
  neighbor 10.255.2.1
    address-family ipv4 unicast
      additional-paths receive
```

## IS-IS for Data Center

### IS-IS Fundamentals

IS-IS (Intermediate System to Intermediate System) is a link-state IGP similar to OSPF.
It is increasingly used as a VXLAN underlay because of its simplicity and scalability.

Key differences from OSPF:
- IS-IS runs directly on L2 (not IP) - uses its own L2 framing
- Uses LSPs (Link State PDUs) instead of LSAs
- Uses CLNS addressing (NET) instead of IP for router identification
- Areas are defined on interfaces, not routers
- No DR/BDR - uses DIS (Designated Intermediate System)

### NET Addressing

IS-IS routers are identified by a NET (Network Entity Title):

```
Format: AFI.Area.SystemID.NSEL
Example: 49.0001.0000.0000.0001.00

AFI:      49 (private addressing)
Area:     0001 (area identifier)
SystemID: 0000.0000.0001 (unique router ID, usually derived from loopback)
NSEL:     00 (selector, always 00 for the router itself)
```

```nxos
feature isis

router isis UNDERLAY
  net 49.0001.0000.0000.0001.00
  is-type level-2
  metric-style wide
  address-family ipv4 unicast
    maximum-paths 64

interface loopback0
  ip address 10.255.1.1/32
  ip router isis UNDERLAY

interface Ethernet1/49
  ip address 10.0.0.0/31
  ip router isis UNDERLAY
  isis network point-to-point
  isis circuit-type level-2
```

### Level-1 and Level-2

| Level | Scope | Equivalent |
|-------|-------|-----------|
| Level-1 | Intra-area | OSPF intra-area |
| Level-2 | Inter-area (backbone) | OSPF inter-area |
| Level-1-2 | Both (default) | OSPF ABR |

In DC underlay, use **Level-2 only** (all routers in same L2 domain):

```nxos
router isis UNDERLAY
  is-type level-2
```

### Wide Metrics and Multi-Topology

Traditional IS-IS uses 6-bit metrics (max 63). Wide metrics (RFC 5305) use 32-bit
metrics, required for TE and large networks.

```nxos
router isis UNDERLAY
  metric-style wide
```

Multi-topology IS-IS can carry IPv4 and IPv6 in separate topologies:

```nxos
router isis UNDERLAY
  address-family ipv4 unicast
  address-family ipv6 unicast
```

### IS-IS as VXLAN Underlay: Comparison

| Feature | OSPF | BGP | IS-IS |
|---------|------|-----|-------|
| Protocol type | Link-state (IP) | Path-vector | Link-state (L2) |
| Addressing | IP Router ID | IP Router ID | NET (CLNS) |
| Convergence | Fast | Medium | Fast |
| Scalability | Good | Excellent | Excellent |
| Unnumbered support | Limited | Yes (link-local) | Native (CLNS) |
| Configuration complexity | Low | Medium | Medium |
| DC adoption | Common | Most common | Growing |
| Multi-vendor | Yes | Yes | Yes |
| Segment Routing | Yes | No (SR-TE) | Yes |

> **CCIE Exam Tip:** IS-IS is less common than OSPF/BGP in DC exams, but it CAN appear
> as the underlay protocol. Know the NET format, Level-1/Level-2, and basic config.
> If the exam gives you IS-IS, the config is actually simpler than OSPF (no area
> assignment per interface, just `ip router isis PROCESS`).

## FHRP (First Hop Redundancy Protocols)

### HSRP (Hot Standby Router Protocol)

HSRP provides a virtual IP/MAC for default gateway redundancy. Cisco proprietary.

- **Active**: forwards traffic for virtual IP
- **Standby**: backup, takes over if active fails
- **Hello**: 3 seconds (default), Hold: 10 seconds
- **Preempt**: higher priority takes over (disabled by default)
- **Virtual MAC**: 0000.0C07.ACxx (xx = group number in hex)

```nxos
feature hsrp

interface vlan 10
  ip address 10.10.10.2/24
  hsrp 10
    preempt
    priority 110
    ip 10.10.10.1
```

### VRRP (Virtual Router Redundancy Protocol)

VRRP is the open-standard equivalent of HSRP (RFC 5798).

- **Master**: forwards traffic
- **Backup**: standby
- **Hello**: 1 second (default)
- **Virtual MAC**: 0000.5E00.01xx (xx = VRID)

```nxos
feature vrrp

interface vlan 10
  ip address 10.10.10.2/24
  vrrp 10
    address 10.10.10.1
    priority 110
    preempt
```

### GLBP (Gateway Load Balancing Protocol)

GLBP load-balances across multiple gateways using a virtual IP with multiple virtual MACs.

- **AVG (Active Virtual Gateway)**: assigns virtual MACs to clients
- **AVF (Active Virtual Forwarder)**: forwards traffic for assigned virtual MAC
- Up to 4 forwarders per group

```nxos
feature glbp

interface vlan 10
  ip address 10.10.10.2/24
  glbp 10
    ip 10.10.10.1
    preempt
    priority 110
    load-balancing round-robin
```

### Anycast Gateway with vPC (HSRP Active/Active)

In a vPC + VXLAN design, the traditional FHRP (HSRP/VRRP) is replaced by the
**Distributed Anycast Gateway**. Both vPC peers share the same virtual IP and MAC.

```nxos
fabric forwarding anycast-gw-mac 0000.1111.2222

interface vlan 10
  ip address 10.10.10.1/24
  fabric forwarding mode anycast-gw
```

Both Leaf-1 and Leaf-2 have:
- Same SVI IP: 10.10.10.1/24
- Same virtual MAC: 0000.1111.2222
- Both respond to ARP for 10.10.10.1

> **CCIE Exam Tip:** In a VXLAN fabric with vPC, you do NOT configure HSRP/VRRP.
> You use `fabric forwarding mode anycast-gw`. This is the DC way. HSRP/VRRP is
> for traditional (non-VXLAN) designs. If the exam asks for FHRP in a VXLAN context,
> the answer is anycast gateway.

### FHRP in VXLAN (Fabric Forwarding)

In a VXLAN fabric, the anycast gateway works across the entire fabric:
1. Host ARPs for gateway IP
2. Local leaf responds with anycast MAC
3. Host sends traffic to local leaf (optimal path)
4. Leaf routes or bridges based on destination
5. If destination is remote VTEP, VXLAN encapsulate and forward

No HSRP election, no standby state, no convergence delay. Every leaf is "active."

```text

show ip arp vlan 10
```

## PBR (Policy Based Routing)

### PBR Fundamentals

PBR overrides the normal routing table decision. Instead of forwarding based on
destination IP, PBR can forward based on source IP, protocol, port, etc.

PBR uses route-maps with match/set statements:

```nxos
route-map PBR_WEB permit 10
  match ip address ACL_WEB
  set ip next-hop 10.0.1.1

route-map PBR_WEB permit 20
  set ip next-hop 10.0.2.1

ip access-list ACL_WEB
  permit tcp 10.10.10.0/24 any eq 80
  permit tcp 10.10.10.0/24 any eq 443

interface vlan 10
  ip policy route-map PBR_WEB
```

### PBR Set Options

- `set ip next-hop X.X.X.X`: forward to specific next-hop
- `set ip next-hop verify-availability X.X.X.X track N`: conditional next-hop
- `set interface null0`: drop matching traffic
- `set vrf VRF_NAME`: forward into a specific VRF

> **CCIE Exam Tip:** PBR is processed BEFORE the routing table. If a PBR route-map
> matches, the routing table is NOT consulted. If no match, normal routing applies.
> PBR is CPU-intensive on some platforms - use with caution.

### Verification Commands - PBR

```text
show route-map
show ip policy
show access-list ACL_WEB
show ip interface vlan 10 | include policy
```

## VRF-Lite

### VRF Fundamentals

A VRF (Virtual Routing and Forwarding) instance is a separate routing table. It provides
L3 isolation (like a VLAN provides L2 isolation).

Key components:
- **RD (Route Distinguisher)**: makes IPv4 prefixes unique across VRFs (8 bytes)
  - Format: ASN:NN (e.g., 65000:100) or IP:NN (e.g., 10.1.1.1:100)
  - RD is NOT used for route filtering - only for uniqueness
- **RT (Route Target)**: controls which routes are imported/exported between VRFs
  - Format: ASN:NN (e.g., 65000:100)
  - `route-target import 65000:100` - accept routes with this RT
  - `route-target export 65000:100` - tag exported routes with this RT
  - `route-target both auto` - auto-generate RT from VNI

### VRF-Lite Configuration

VRF-Lite is VRF without MPLS. Routes are exchanged between VRFs using MP-BGP or
static routes with route leaking.

```nxos
vrf context PROD
  rd 65000:100
  address-family ipv4 unicast
    route-target import 65000:100
    route-target export 65000:100

vrf context DEV
  rd 65000:200
  address-family ipv4 unicast
    route-target import 65000:200
    route-target export 65000:200

interface vlan 10
  vrf member PROD
  ip address 10.10.10.1/24

interface vlan 20
  vrf member DEV
  ip address 10.20.20.1/24
```

### MP-BGP for VRF Route Exchange

MP-BGP (Multi-Protocol BGP) carries VRF routes between routers:

```nxos
router bgp 65000
  vrf PROD
    address-family ipv4 unicast
    neighbor 10.255.2.1
      remote-as 65000
      update-source loopback0
      address-family ipv4 unicast
        send-community extended
```

### VRF Route Leaking (Inter-VRF Routing)

To allow communication between VRFs (e.g., PROD to DEV):

```nxos
router bgp 65000
  vrf PROD
    address-family ipv4 unicast
      export map LEAK_TO_DEV

route-map LEAK_TO_DEV permit 10
  match ip address prefix-list PROD_SUBNETS
  set extcommunity rt 65000:200 additive
```

> **CCIE Exam Tip:** In VXLAN, VRFs map to L3VNIs. The RD and RT are often auto-derived
> from the VNI (`route-target both auto`). You rarely configure RD/RT manually in a
> VXLAN fabric. But for VRF-Lite (non-VXLAN) or L3Out, you configure them explicitly.

## Underlay Routing Design Comparison

### OSPF vs BGP vs IS-IS for VXLAN Underlay

| Criteria | OSPF | BGP (unnumbered) | IS-IS |
|----------|------|-------------------|-------|
| **Best for** | Small-medium fabrics | Large fabrics, multi-vendor | SP-grade fabrics |
| **Scalability** | ~100 nodes | 1000+ nodes | 1000+ nodes |
| **Convergence** | Fast (SPF) | Medium (path-vector) | Fast (SPF) |
| **Config complexity** | Low | Medium | Medium |
| **Unnumbered links** | Limited | Native (link-local) | Native (CLNS) |
| **Addressing overhead** | /30 or /31 per link | None (link-local) | None (CLNS) |
| **Multi-vendor** | Yes | Yes | Yes |
| **Segment Routing** | Yes (OSPF-SR) | No (use SR-TE) | Yes (IS-IS SR) |
| **DC exam frequency** | High | Highest | Low |
| **Route policy** | Limited | Excellent (communities) | Limited |

### Recommendation for CCIE DC Exam

1. **BGP EVPN underlay** (most common in exam): Use BGP for both underlay and overlay.
   Spines are route reflectors. Leaves peer with spines. Unnumbered or numbered.

2. **OSPF underlay + BGP EVPN overlay**: OSPF for underlay reachability, BGP for EVPN.
   Simpler BGP config (only EVPN AF needed).

3. **IS-IS underlay**: Rarely tested but know the basics.

> **CCIE Exam Tip:** The exam will tell you which underlay to use. Read the task
> carefully. If it says "BGP underlay," use BGP for both underlay and EVPN. If it
> says "OSPF underlay," use OSPF for underlay and BGP for EVPN overlay only.

### Topology

              |    Spine-1        |     |    Spine-2        |
              |  10.255.100.1     |     |  10.255.100.2     |
              +--+-----+-----+---+     +---+-----+-----+---+
                 |     |     |             |     |     |

## Lab 2: BGP EVPN Underlay (Unnumbered)

### Topology

Same physical topology as Lab 1, but using BGP unnumbered for underlay.

```
              +-------------------+     +-------------------+
              |    Spine-1        |     |    Spine-2        |
              |  AS 65001         |     |  AS 65001         |
              |  RR (reflector)   |     |  RR (reflector)   |
              +--+-----+-----+---+     +---+-----+-----+---+
                 |     |     |             |     |     |
            eBGP  |     |     |        eBGP |     |     |
                 |     |     |             |     |     |
              +--+--+--+--+--+--+       +--+--+--+--+--+--+
              | Leaf-1      |           | Leaf-2      |
              | AS 65002    |           | AS 65003    |
              +-------------+           +-------------+

Underlay: eBGP unnumbered (link-local peering)
Overlay: iBGP EVPN (loopback peering, RR on spines)
```

### Spine-1 Configuration

```nxos
hostname Spine-1

feature bgp
feature interface-vlan

interface loopback0
  ip address 10.255.100.1/32

interface Ethernet1/1
  no switchport
  ipv6 enable
  no shutdown

interface Ethernet1/2
  no switchport
  ipv6 enable
  no shutdown

router bgp 65001
  router-id 10.255.100.1
  address-family l2vpn evpn
    retain route-target all

  template peer SPINE_UNDERLAY
    remote-as 65001
    update-source loopback0
    ebgp-multihop 2
    address-family ipv4 unicast
      send-community extended
    address-family l2vpn evpn
      send-community extended
      route-reflector-client

  neighbor 10.255.1.1
    inherit peer SPINE_UNDERLAY
  neighbor 10.255.2.1
    inherit peer SPINE_UNDERLAY
```

### Leaf-1 Configuration

```nxos
hostname Leaf-1

feature bgp
feature nv overlay
feature vn-segment-vlan-based
feature interface-vlan

interface loopback0
  ip address 10.255.1.1/32

interface Ethernet1/49
  no switchport
  ipv6 enable
  no shutdown

interface Ethernet1/50
  no switchport
  ipv6 enable
  no shutdown

router bgp 65002
  router-id 10.255.1.1
  address-family l2vpn evpn
    retain route-target all

  neighbor 10.255.100.1
    remote-as 65001
    update-source loopback0
    ebgp-multihop 2
    address-family ipv4 unicast
      send-community extended
    address-family l2vpn evpn
      send-community extended

  neighbor 10.255.100.2
    remote-as 65001
    update-source loopback0
    ebgp-multihop 2
    address-family ipv4 unicast
      send-community extended
    address-family l2vpn evpn
      send-community extended
```

## Troubleshooting Labs

### Scenario 1: OSPF Neighbor Not Forming

**Symptom**: `show ip ospf neighbors` shows no neighbors on an interface.

**Checklist**:
1. Interface is up/up: `show interface Ethernet1/49`
2. IP addresses are in same subnet: `show ip interface brief`
3. OSPF is enabled on interface: `show ip ospf interface Ethernet1/49`
4. Area matches: both must be in same area
5. Hello/Dead timers match: `show ip ospf interface` (check timers)
6. Network type matches: both point-to-point or both broadcast
7. MTU matches: OSPF checks MTU in DBD packets
8. Authentication matches (if configured)
9. ACL not blocking OSPF (multicast 224.0.0.5/6)

```text
Leaf-1# show ip ospf interface Ethernet1/49
Ethernet1/49 is up, line protocol is up
  IP address 10.0.1.1/31
  Process ID UNDERLAY, Router ID 10.255.1.1, Network Type POINT_TO_POINT
  Hello 10, Dead 40, Wait 40, Retransmit 5
```

### Scenario 2: BGP Session Not Establishing

**Symptom**: `show bgp summary` shows neighbor in Idle or Active state.

**Checklist**:
1. TCP connectivity to peer: `ping 10.255.2.1 source loopback0`
2. IGP has route to peer loopback: `show ip route 10.255.2.1`
3. AS number matches: local config vs neighbor's config
4. Update-source is correct: must be reachable from peer
5. ebgp-multihop set (if not directly connected)
6. No ACL blocking TCP 179
7. BGP not already peering from another source

```text
Leaf-1# show bgp neighbors 10.255.100.1
BGP neighbor is 10.255.100.1,  remote AS 65001, ibgp link, Peer index 1
  BGP state = Established, up for 00:10:05
  Using loopback0 as update source
```

### Scenario 3: VRF Route Not Appearing

**Symptom**: Route exists in VRF PROD on Leaf-1 but not on Leaf-2.

**Checklist**:
1. Route is in BGP VRF table: `show bgp vrf PROD ipv4 unicast`
2. Route has correct RT: check extended community
3. Peer VRF imports matching RT: `show vrf PROD detail`
4. BGP session for VRF is up: `show bgp vrf PROD ipv4 unicast summary`
5. Route-map not filtering the route
6. RD is unique (duplicate RD causes route confusion)

```text
Leaf-1# show bgp vrf PROD ipv4 unicast 10.10.10.0/24
BGP routing table information for VRF PROD
Route Distinguisher: 65000:100
Route Type: Network
    Next Hop: 10.255.1.1
    Extended Community: RT:65000:100
```

## Common Exam Scenarios

### Scenario 1: BGP EVPN Underlay Build (Deploy Module)

**Task**: "Configure BGP EVPN with spines as route reflectors. Leaves peer with both spines. AS 65000."

**Time budget**: 20-25 minutes (for 4 leaves + 2 spines).

**Execution order**:
1. `feature bgp` on all nodes
2. Loopback0 with IP (for peering)
3. Underlay routing (OSPF or BGP unnumbered) to reach loopbacks
4. On spines: `router bgp 65000`, neighbor per leaf, `route-reflector-client`, `send-community extended`
5. On leaves: `router bgp 65000`, neighbor per spine, `send-community extended`
6. `address-family l2vpn evpn` on ALL neighbors
7. Verify: `show bgp l2vpn evpn summary` (all Established)

**Zero-credit mistakes**:
- Missing `address-family l2vpn evpn` under neighbor (session up but no EVPN routes)
- Missing `send-community extended` (routes propagated without RT, not imported)
- Missing `route-reflector-client` on spine (spine won't reflect leaf-to-leaf routes)

### Scenario 2: OSPF Underlay Not Converging (Troubleshoot Module)

**Task**: "Leaf-1 cannot reach Spine-2 loopback. OSPF neighbor is stuck in INIT state."

**Diagnosis**:
```text
Leaf-1# show ip ospf interface Ethernet1/50
  Network Type: BROADCAST    <-- Should be POINT_TO_POINT
  Hello 10, Dead 40

Spine-2# show ip ospf interface Ethernet1/2
  Network Type: POINT_TO_POINT
  Hello 10, Dead 40
```

**Root Cause**: Network type mismatch. One side is broadcast (default for Ethernet), other is point-to-point.

**Fix**: Set both sides to `ip ospf network point-to-point`.

### Scenario 3: VRF Route Leaking Between Tenants (Configure Module)

**Task**: "Allow VRF PROD to reach VRF DEV subnet 10.20.20.0/24 via route leaking."

**Config**:
```nxos
route-map LEAK_PROD_TO_DEV permit 10
  match ip address prefix-list PROD_SUBNETS
  set extcommunity rt 65000:200 additive

router bgp 65000
  vrf PROD
    address-family ipv4 unicast
      export map LEAK_PROD_TO_DEV
```

**Verification**: `show ip route vrf DEV` must show 10.20.20.0/24 with next-hop via BGP.

**Common mistake**: Forgetting `additive` keyword (replaces existing RT instead of adding), or forgetting the import RT on the destination VRF.

> **Lab Exam Warning:** L3 protocol tasks are the FOUNDATION of the exam. If your
> underlay doesn't converge, NOTHING else works. Always verify underlay FIRST:
> `show ip ospf neighbors` or `show bgp summary` before touching overlay config.
> A 5-minute underlay verification saves 30 minutes of overlay troubleshooting.

## Key Takeaways

1. **OSPF**: Use single Area 0 for DC underlay. Point-to-point network type on
   spine-leaf links. /31 subnets. BFD for fast detection. Per-VRF OSPF for L3 services.

2. **BGP**: The DC workhorse. EVPN AF for overlay, IPv4 AF for underlay. Route
   reflectors on spines. Know all 13 path selection steps. Unnumbered underlay
   eliminates IP addressing on links.

3. **IS-IS**: Alternative underlay. NET addressing, Level-2 only, wide metrics.
   Simpler than OSPF in some ways. Know it but expect BGP/OSPF more often.

4. **FHRP**: In VXLAN fabrics, use anycast gateway (not HSRP/VRRP). Both vPC peers
   share same IP and MAC. No election, no convergence delay.

5. **PBR**: Overrides routing table. Route-map with match/set. Use sparingly.

6. **VRF-Lite**: Separate routing tables. RD for uniqueness, RT for import/export.
   In VXLAN, VRFs map to L3VNIs with auto RT/RD.

> **Lab Exam Warning:** The underlay is the FOUNDATION. If your underlay is broken,
> NOTHING works - no VXLAN, no EVPN, no L3 services. Always verify underlay first:
> `show ip route` (or `show bgp summary`), then `show nve peers`, then EVPN routes.
> Troubleshoot bottom-up: L1 -> L2 -> Underlay -> Overlay -> Services.
